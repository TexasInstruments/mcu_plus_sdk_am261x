Overview

Running PSRAM at 133 MHz in Mode 2 (8D-8D-8D DDR octal) requires the Core PLL to be configured at 2000 MHz so that its HSDIV0 CLKOUT3 output divides down to exactly 133 MHz. This PLL configuration cannot be produced by the default SysCfg-generated clock tree code, so a specific set of steps is required in both the SBL and in every application that uses OSPI with this clock.

Note
This guide applies to AM261x only.

Prerequisites: Core PLL at 2000 MHz

Both OSPI instances (OSPI0 for flash, OSPI1 for PSRAM) share the same clock source — DPLL_CORE_HSDIV0_CLKOUT3. For that output to be 133 MHz, the Core APLL must be locked at 2000 MHz (FOUT = 2000 MHz, HSDIV3 divides by 15 → 133.33 MHz).

The default SysCfg clock tree code does not produce this configuration. The bootloader's Bootloader_socConfigurePll() does — but only if it is allowed to run in place of the SysCfg generated PLL initialisation.

Step 1 — SBL: Exclude the SysCfg PLL config and let the bootloader default run

SysCfg normally generates ti_clocktree_pll_config.c, which is compiled into the SBL and initialises the PLLs. To use the 133 MHz OSPI clock, this file must be excluded from the SBL build so that the bootloader falls back to its own built-in PLL configuration.

This requires changes in two places.

1a — SysCfg: mark the file excluded from build

In the SBL .syscfg file, add the following line at the top:

scripting.excludeFromBuild("ti_clocktree_pll_config.c");

1b — Makefile: remove the source file and update SYSCFG_GEN_FILES

SysCfg propagates the excludeFromBuild hint into the generated file list, but the hand-maintained makefile must also be updated manually. Two changes are needed:

1. Remove ti_clocktree_pll_config.c from FILES_common:

# Standard SBL makefile (e.g. sbl_null) — includes the file:
FILES_common := \
main.c \
...
ti_power_clock_config.c \
ti_clocktree_pll_config.c \ # <-- remove this line
# sbl_ospi_psram_xip makefile — file is absent:
FILES_common := \
main.c \
...
ti_power_clock_config.c \

2. Remove generated/ti_clocktree_pll_config.c from SYSCFG_GEN_FILES, keeping only the header:

# Standard SBL (both .c and .h declared as generated outputs):
SYSCFG_GEN_FILES+=generated/ti_clocktree_pll_config.c generated/ti_clocktree_pll_config.h
# sbl_ospi_psram_xip (only .h declared — .c is still generated but not compiled):
SYSCFG_GEN_FILES+=generated/ti_clocktree_pll_config.h

Removing the .c from SYSCFG_GEN_FILES means the build system no longer treats it as a dependency target, so it will not be passed to the compiler even if it is regenerated by SysCfg.

Why this works

With ti_clocktree_pll_config.c absent from the build, the linker resolves Bootloader_socConfigurePll() from bootloader_soc.c instead. That function is declared __attribute__((weak)), so it is used automatically whenever no other definition is linked in. It configures the Core APLL at 2000 MHz and sets HSDIV0 CLKOUT3 to 133 MHz for both the 400 MHz and 500 MHz R5F frequency variants:

// source/drivers/bootloader/soc/am261x/bootloader_soc.c
__attribute__((weak)) void Bootloader_socConfigurePll(void)
{
// 400 MHz R5F variant:
// hsDivOutFreqHz[3] = 133 MHz → DPLL_CORE_HSDIV0_CLKOUT3
// SOC_rcmCoreApllConfig(RCM_PLL_FOUT_FREQID_CLK_2000MHZ, ...)
// 500 MHz R5F variant:
// hsDivOutFreqHz[3] = 133 MHz → DPLL_CORE_HSDIV0_CLKOUT3
// SOC_rcmCoreApllConfig(RCM_PLL_FOUT_FREQID_CLK_2000MHZ, ...)
...
}

Step 2 — SBL and Application: Override the OSPI input clock frequency in SysCfg

Because the SysCfg clock tree no longer drives the OSPI clock configuration, the OSPI module cannot derive the correct input frequency automatically. You must override it manually.

For every SysCfg project (SBL and application) that uses OSPI with this clock source:

  1. In the OSPI peripheral configuration, verify that Clock Source is set to DPLL_CORE_HSDIV0_CLKOUT3.
  2. Enable Override Input Clock Frequency.
  3. Set Custom Input Clock Frequency (Hz) to 133333333.

In the .syscfg file this appears as:

// OSPI1 (PSRAM)
ram1.serialRamDriver.peripheralDriver.overrideInputClkFreq = true;
ram1.serialRamDriver.peripheralDriver.customInputClkFreq = 133333333;
// OSPI0 (Flash, if also present)
flash1.peripheralDriver.overrideInputClkFreq = true;
flash1.peripheralDriver.customInputClkFreq = 133333333;
Warning
Enabling the override bypasses the automatic frequency derivation. Ensure the value entered exactly matches the actual clock delivered to the OSPI peripheral. An incorrect value will misconfigure the baud-rate divider and PHY timing parameters, potentially causing data corruption or flash/PSRAM communication failures.

Important: Flash is also capped at 133 MHz

OSPI0 (flash) and OSPI1 (PSRAM) share DPLL_CORE_HSDIV0_CLKOUT3 as their clock source. Once the Core PLL is locked at 2000 MHz and CLKOUT3 is set to 133 MHz, both peripherals are limited to a maximum input clock of 133 MHz. There is no way to run flash at a higher frequency while PSRAM uses this clock source.

Step 3 — Every downstream application that uses OSPI

From the point at which the SBL applies this PLL configuration, the Core PLL remains at 2000 MHz for the lifetime of the device session. Any application loaded by that SBL and using OSPI0 or OSPI1 must also have the clock override set (Step 2 above), because SysCfg will still attempt to derive the input frequency from the clock tree and will compute the wrong value unless the override is in place.

This applies equally to applications using the flash driver (OSPI0) and to applications using the PSRAM driver (OSPI1).

Reference Example

The sbl_ospi_psram_xip example located at

examples/drivers/boot/sbl_ospi_psram_xip/am261x-lp/r5fss0-0_nortos/

demonstrates the complete configuration described in this guide:

  • example.syscfg line 8: scripting.excludeFromBuild("ti_clocktree_pll_config.c");
  • OSPI1 (PSRAM): overrideInputClkFreq = true, customInputClkFreq = 133333333
  • OSPI0 (Flash): overrideInputClkFreq = true, customInputClkFreq = 133333333

Use this example as the starting point for any SBL that needs to boot from PSRAM at 133 MHz.
